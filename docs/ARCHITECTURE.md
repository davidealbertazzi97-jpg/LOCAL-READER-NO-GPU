# Architecture

```text
browser on 127.0.0.1
        |
        | token + exact origin
        v
bounded FastAPI boundary ──> SQLite job metadata
        |
        | private bounded work copy
        v
serialized job runner
        |
        +── isolated PaddleOCR Python ──> document.json
        |                                  accessible.html
        |                                  reading.txt
        |
        +── isolated llama.cpp process ──> reflowed reading.txt (Solo organizza)
        |
        +── isolated Kokoro ONNX Python ──> speech.mp3 (offline)
        |
        └── isolated cloud workers ──────> speech.mp3 (chosen provider)

work copy removed ────────────────> durable results remain
```

The web core, OCR stack, and speech stack use separate virtual environments.
OCR runs the plain `PaddleOCR` pipeline on CPU with document orientation,
unwarping, text-line orientation, and PP-Structure disabled. This produces
linear text and intentionally does not reconstruct tables. PaddleOCR models
are prefetched during installation and then used from the local PaddleX cache.

PDF/image processing is bounded by the existing upload, page, pixel, and frame
limits. `document.json` is the editable source of truth; every revision is
validated and exports are regenerated by escaping text into a fixed HTML
template.

Pasted text and OCR text share the same `reading.txt` boundary. The optional
LFM2.5 230M worker sends bounded chunks to `llama.cpp` with reasoning disabled.
Its output is accepted only when every non-whitespace character is identical
to the input; otherwise the deterministic whitespace-only formatter is used.

The complete workflow intentionally skips reflow: it is PaddleOCR followed by
Edge-TTS. LFM is available only from explicit organization actions, so a user
who wants the original OCR text is not forced through a generative model.

Edge-TTS, Kokoro, and cloud speech engines all receive bounded chunks and
produce one MP3. Edge-TTS and cloud providers are deliberately isolated from
the local network guard; the selected provider receives text only for that
job. Kokoro uses the local ONNX model and needs no network. API keys are read
from a private settings file and passed to child workers through a short-lived
0600 configuration file, never through browser responses or process arguments.
